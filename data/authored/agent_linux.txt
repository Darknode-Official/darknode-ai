Users, groups, and the meaning of UID 0

On Linux the security boundary that matters most is not a username but a numeric user id. The kernel authorizes actions by UID and GID, and the name is a convenience resolved through /etc/passwd, /etc/group, and whatever NSS sources are configured (LDAP, SSSD, systemd-userdb). A defender auditing accounts should therefore reason in numbers first. Any account with UID 0 is root, regardless of what it is called; a rogue "backup" line that reads backup:x:0:0 in /etc/passwd is a full root account hiding behind an innocuous name. Check for it with awk -F: '($3==0){print}' /etc/passwd, and expect exactly one result. Duplicate UIDs are equally dangerous because two names then share one identity and one home-directory trust relationship. System accounts (UID below 1000 on most distributions, governed by UID_MIN in /etc/login.defs) should have a non-login shell such as /usr/sbin/nologin or /bin/false; a service account with /bin/bash is a common misconfiguration that widens the blast radius of a compromised daemon. Group membership grants standing privilege: members of sudo (Debian) or wheel (RHEL) can escalate, members of docker or lxd effectively have root because they control a daemon that runs as root, and members of disk can read raw block devices and bypass filesystem permissions entirely. Enumerating who belongs to these groups is a first-day hardening task, not an incident-only one.
<<<DOC>>>
File permission bits, and why the third octal digit matters

The classic rwxrwxrwx model answers three questions for owner, group, and everyone else: may I read, write, execute. Defenders internalize this quickly, but the special bits in the leading fourth octal digit are where privilege escalation lives. The setuid bit (4000) makes an executable run with the file owner's identity rather than the caller's; setgid (2000) does the same for the group, and on directories it makes new files inherit the directory's group. The sticky bit (1000) on a world-writable directory such as /tmp restricts deletion to the file owner, which is why anyone can create files in /tmp but cannot delete a neighbor's. A defender's instinct on seeing -rwsr-xr-x is to ask: does this binary legitimately need to cross a privilege boundary? passwd needs setuid-root because it edits /etc/shadow; a random binary in /home or /tmp with the setuid bit set almost never does and is a strong persistence or escalation signal. Enumerate the whole filesystem with find / -xdev -perm -4000 -type f 2>/dev/null and compare the result against a known-good baseline from a fresh install of the same distribution. The comparison is the point: the list on its own is noise, the diff is signal.

Reading /etc/passwd and /etc/shadow like an auditor

/etc/passwd is world-readable by design and carries seven colon-separated fields: name, password placeholder, UID, GID, GECOS comment, home directory, login shell. The password field almost always shows x, meaning the real hash lives in /etc/shadow, which is readable only by root and the shadow group. A defender scanning /etc/passwd looks for anomalies: an empty second field (login with no password), a UID of 0 on any line but root, a home directory pointing somewhere writable by others, or a login shell on an account that should be a daemon. In /etc/shadow the fields encode the hashed password and aging policy. A hash beginning with $6$ is SHA-512, $y$ is yescrypt (the modern default on newer distributions), and a bare * or ! means the account cannot authenticate with a password at all, which is the desired state for service accounts. A field that is empty where a hash should be is a passwordless account and a finding. Password aging fields govern minimum and maximum age and warning periods; accounts that never expire and never require a change are policy gaps rather than active compromises, but they belong in the audit report. The honest analyst notes that reading these files tells you the current state, not how it got there; correlating mtimes and auth logs supplies the history.

sudo, sudoers, and the quiet ways it goes wrong

sudo is the sanctioned path from an unprivileged user to elevated commands, and its configuration in /etc/sudoers and the drop-in files under /etc/sudoers.d is a high-value audit target. The safe way to read the effective policy is visudo -c for syntax and, for a given user, sudo -l run as that user, which enumerates exactly what they may run. The dangerous patterns are learnable. A line granting ALL=(ALL) NOPASSWD: ALL removes the password gate entirely, so a stolen session cookie or an unlocked terminal becomes instant root. A rule permitting a single "harmless" binary can still be total if that binary can spawn a shell or write arbitrary files; editors, pagers, language interpreters, and archive tools with a shell-escape are the classic examples, which is why defenders cross-reference allowed commands against the known set of programs that can break out. Wildcards in command arguments are treacherous because the shell and sudo parse them differently than an author expects. The secure-path setting matters too: if sudo does not reset PATH, a user-writable directory early in PATH lets an attacker substitute a trojaned helper that the elevated command then calls. Auditing sudo is not only reading the files; it is reasoning about what each grant composes into.

Processes: what ps and /proc actually tell you

When a defender lists processes with ps aux or ps -ef, they are reading a snapshot the kernel exposes through /proc, one numbered directory per PID. The columns worth scrutiny are the running user, the parent PID, the start time, and the full command line. A shell whose parent is a web server or a database is worth a second look because interactive shells do not normally descend from daemons. The command line in ps can be spoofed, since a process may rewrite its own argv, so a careful analyst corroborates with the fields the process cannot easily forge: /proc/PID/exe is a symlink to the real executable on disk, /proc/PID/cwd shows the working directory, and /proc/PID/environ (readable only by the owner and root) reveals the environment it was launched with. A telling anomaly is /proc/PID/exe pointing at a path marked "(deleted)", meaning the binary was unlinked from the filesystem while still running, a common way to hide a payload from file scans while it executes from memory. Open files and sockets tie a process to the network and disk: ls -l /proc/PID/fd, or the friendlier lsof -p PID. None of this proves malice by itself; a deleted-executable process can be a legitimately updated daemon that has not restarted. The method is to gather the observable facts, then reason about which benign and malicious explanations fit.

Listening sockets and the ss command

Every network service is ultimately a process holding a listening socket, and enumerating those sockets is how a defender learns the real attack surface rather than the documented one. The modern tool is ss, which reads kernel socket state directly; ss -tulpen shows TCP and UDP listeners with the owning process, the user, and the inode. The classic netstat gives similar output on older systems. The first question is not "what ports are open" but "does every listener correspond to a service we intended to run." A listener bound to 0.0.0.0 or :: is reachable from any interface, whereas one bound to 127.0.0.1 is local only; a database that should be loopback-only but shows a wildcard bind is a misconfiguration that exposes it to the network. The owning process matters: a listener owned by an unexpected user, or by a process whose executable lives in /tmp or a user home, is a strong signal. Ephemeral high ports with no recognizable service are worth pivoting into the process. A rigorous audit compares the live listener set against an approved baseline and against the firewall policy, because a port that is listening but firewalled is a latent risk, and a port that is firewalled today may be exposed tomorrow when a rule changes. The socket table is ground truth for exposure; the documentation is only a claim.

systemd units as a persistence surface

systemd is the init system on most contemporary distributions, and its unit files are both the legitimate way services start and a favored place for persistence because a unit can quietly relaunch a payload after every reboot. Units load from a search path with a precedence order: /etc/systemd/system overrides /run/systemd/system overrides /usr/lib/systemd/system, so an attacker who can write to /etc can shadow or add a service without touching packaged files. A defender enumerates active and enabled units with systemctl list-units --type=service and systemctl list-unit-files --state=enabled, then inspects suspicious ones with systemctl cat, which prints the effective unit including drop-in overrides under name.service.d. The fields that carry execution are ExecStart, ExecStartPre, and ExecStartPost; a value pointing into /tmp, /dev/shm, a user home, or a base64-decoding shell one-liner deserves scrutiny. Timers (name.timer) are the systemd analogue of cron and are easy to overlook, so list them with systemctl list-timers. User-level units under ~/.config/systemd/user run without root and survive via lingering, which is enabled per user and often unmonitored. The disciplined approach is to diff the current unit inventory against a baseline and to treat any unit whose on-disk file postdates the last legitimate change window as a lead to run down.

cron, its many files, and the attacker's love of it

cron schedules commands, and its configuration is scattered enough that a hurried audit misses half of it. Per-user schedules live in the spool, typically /var/spool/cron/crontabs on Debian or /var/spool/cron on RHEL, and are edited through crontab -e rather than by hand. The system-wide file /etc/crontab and the drop-in directory /etc/cron.d hold entries that include a run-as user field, so a line there can execute as root. The convenience directories /etc/cron.hourly, cron.daily, cron.weekly, and cron.monthly run every executable script they contain, which makes dropping a file into cron.daily a tidy persistence trick that never edits a crontab at all. A defender enumerates all of these, plus the at queue in /var/spool/cron/atjobs and any anacron configuration, and checks /etc/cron.allow and /etc/cron.deny to see who is even permitted to schedule jobs. The signals are familiar: a job that curls a remote script and pipes it to a shell, an entry that writes to an SSH authorized_keys file, a script whose mtime is recent and whose owner is unexpected, or an obfuscated one-liner. As always the baseline diff is more informative than the raw listing, because most cron entries are legitimate and the anomaly is what earns investigation.

SSH server configuration and the settings that matter

The SSH daemon is the front door to most Linux hosts, and its configuration in /etc/ssh/sshd_config concentrates a great deal of security in a few directives. PermitRootLogin should be no, or at most prohibit-password, so that root cannot be brute-forced directly and every privileged action is attributable to a named user who then escalates. PasswordAuthentication no forces key-based login, which defeats credential-stuffing against the service, provided keys are managed well. AllowUsers or AllowGroups restrict who may authenticate at all, shrinking the surface to an explicit list. Defenders also watch for weaker choices: PermitEmptyPasswords yes is catastrophic, an overly permissive AuthorizedKeysFile or an AuthorizedKeysCommand that trusts an external source can be subverted, and X11Forwarding or agent forwarding enabled broadly can leak trust to intermediate hosts. After editing, the config is validated with sshd -t before restart so a typo does not lock everyone out. Reading the file is necessary but not sufficient, because Include directives and Match blocks can override globals for particular users, groups, or source addresses; the effective policy for a given connection is what Match resolves to, which sshd -T -C reveals for a specified connection context. An auditor reasons about the composed policy, not the first matching line they happen to read.
<<<DOC>>>
authorized_keys: the most durable backdoor

Public-key authentication in SSH is trust anchored in a file: ~/.ssh/authorized_keys in each user's home, or a path set by AuthorizedKeysFile. Any public key listed there can log in as that user without a password, which makes the file the single most common and durable persistence mechanism defenders find, because it survives reboots, package updates, and password changes, and it rarely triggers alarms. An audit reads every user's authorized_keys, including root's, and asks for each line: whose private key is this, and was it authorized through our provisioning process. The key comment field at the end of a line is a hint but is attacker-controllable, so it is a lead, not proof. The dangerous elaborations live in the key options that can prefix a line. A command= option pins the key to a single command, which is good when we set it and suspicious when we did not; a from= option restricts source addresses; but options like no-pty absence, or a forced command that is actually a shell, can hide intent. Equally important is the file's own security: authorized_keys must not be group- or world-writable, the .ssh directory must be mode 700, and the home directory must not be writable by others, or sshd will refuse the key. A defender also watches mtime and compares the key set against an inventory, since a key appearing outside a change window is exactly the anomaly worth chasing.

Reading auth.log and journald without fooling yourself

Authentication events are the spine of most Linux investigations. On Debian-family systems they land in /var/log/auth.log; on RHEL-family systems in /var/log/secure; and increasingly the authoritative source is the systemd journal, queried with journalctl, for example journalctl _COMM=sshd or journalctl -u ssh since a timestamp. The lines to know are "Accepted publickey" and "Accepted password" (a successful login, with user and source IP), "Failed password" (a rejected attempt), "Invalid user" (a login for a nonexistent account, typical of scanning), and sudo's own lines recording who ran what as whom. A defender reads these for patterns rather than single events: a burst of failures from one IP is a brute-force attempt, but a single Accepted after many Failed from the same IP is the more alarming success-after-guessing. Honesty about limits matters here. Timestamps reflect the host clock, which may be wrong or manipulated; source IPs can be proxied or spoofed for UDP; and an attacker with root can edit text logs, which is why forwarding logs off-host in real time is a control, not a nicety. The journal is somewhat harder to tamper with quietly and supports cryptographic sealing with Forward Secure Sealing, but nothing on a fully compromised host is trustworthy in place. The discipline is to state what the log shows, note that logs can lie, and corroborate across independent sources.

Privilege-escalation enumeration, seen from the defender's chair

Attackers run enumeration to find a path from a low-privileged foothold to root; defenders run the same enumeration to find and close those paths first. The value is entirely in doing it before an adversary does. The checklist is well worn. Setuid and setgid binaries: find them and diff against baseline, because an unexpected one may allow a shell escape. Sudo rights: sudo -l per account, hunting for NOPASSWD grants and for allowed programs that can break out. Writable files owned by root that are executed by privileged processes: a cron script, a systemd ExecStart, or a service's config that a non-root user can edit is a direct escalation. World-writable directories in the PATH of privileged jobs. Capabilities on files, which are a quieter cousin of setuid: getcap -r / reveals binaries granted specific powers such as cap_setuid, and one carrying that capability can be as dangerous as setuid-root. Kernel and package versions matched against known-vulnerable ranges, understanding that a version match is a hypothesis about exposure, not proof of exploitability. Credentials left in world-readable config files, history files, or environment. The defender's output is a remediation list ranked by how directly each item leads to root, and the mindset is to assume the foothold already exists and ask what it could reach.

Linux capabilities: setuid's fine-grained successor

The all-or-nothing split between root and everyone else was always too coarse, so Linux introduced capabilities to slice root's power into discrete privileges that can be granted to a process or attached to a file. A web server can hold cap_net_bind_service to bind port 80 without otherwise being root; a network tool can hold cap_net_raw to craft packets. This is a hardening win when used to reduce privilege, but file capabilities are also a persistence and escalation surface that pure setuid scans miss. A defender enumerates them with getcap -r / 2>/dev/null and evaluates each result against intent. The capabilities that approximate full root are the ones to flag: cap_setuid and cap_setgid let a process change identity, cap_dac_override bypasses file permission checks, cap_sys_admin is so broad it is jokingly called the new root, cap_sys_ptrace allows attaching to other processes, and cap_sys_module allows loading kernel modules. A binary that legitimately needs none of these but carries cap_setuid is as much a finding as a setuid-root binary in /tmp. Capabilities also apply to running processes and containers; a container granted cap_sys_admin has escaped most of its isolation. The auditing lesson is that "no setuid binaries" is not the same as "no privileged binaries," and a thorough baseline records both.

File integrity monitoring and the discipline of baselines

Most of the audits in this corpus reduce to one idea: you cannot recognize an anomaly without a definition of normal, and a baseline is that definition made concrete. File integrity monitoring captures cryptographic hashes and metadata of the files that matter, stores that record somewhere the monitored host cannot quietly rewrite, and periodically re-checks the live system against it. Tools like AIDE, Tripwire, and the integrity features of some EDR products implement this, and even a homegrown manifest of sha256 sums is far better than nothing. The files worth watching are the ones an attacker must touch to persist or escalate: binaries in the system PATH, the contents of /etc, kernel and initramfs images, systemd units, cron directories, PAM configuration, and every authorized_keys. The subtleties are what make it useful. Package updates legitimately change many of these, so the baseline must be reconciled after each maintenance window or it drowns the analyst in expected diffs. The hash database itself is a target, so it belongs off-host or on read-only media; a database an attacker can edit records only the reality the attacker permits. And integrity monitoring detects change after the fact, so it pairs with prevention rather than replacing it. Reconciled diligently, though, a baseline turns the vague question "is this host clean" into the answerable question "what changed, and was it authorized."

PAM: where authentication policy actually lives

Pluggable Authentication Modules sit beneath login, sudo, sshd, and cron, deciding through a stack of modules whether an authentication succeeds and what happens around it. The configuration under /etc/pam.d, one file per service plus shared includes like common-auth or system-auth, is powerful and easy to weaponize precisely because so few operators read it closely. Each line names a management group (auth, account, password, session), a control such as required or sufficient, and a module such as pam_unix.so or pam_faillock.so. A defender auditing PAM watches for a few things. An added module line pointing at a shared object outside the standard directories, or a module with an unusual name, can be an authentication backdoor that accepts a hardcoded credential; because PAM sits below every login path, such a change is both stealthy and total. A pam_permit.so placed where it should not be will accept anything. Missing hardening modules are the quieter finding: no pam_faillock or pam_tally2 means no lockout after repeated failures, and a weak or absent pam_pwquality means trivial passwords are allowed. Because the files are includes of includes, the effective stack for a service is a composition, so the auditor traces the whole chain rather than one file. Baselining /etc/pam.d and alerting on any change is proportionate, since legitimate edits here are rare and adversarial edits here are devastating.

Namespaces and the reality behind "containers"

A Linux container is not a distinct kernel object; it is an ordinary process that the kernel has placed into a set of namespaces and constrained with cgroups, capabilities, and often seccomp and an LSM profile. Namespaces virtualize a global resource for the process: the mount namespace gives it its own filesystem view, the PID namespace its own process-number space so it sees itself as PID 1, the network namespace its own interfaces and routes, and there are user, UTS, IPC, and time namespaces as well. Understanding this demystifies both isolation and escape. The isolation is only as strong as the narrowest constraint, so a container that shares the host PID namespace, mounts the host filesystem, runs as UID 0 mapped to real root, or is granted a dangerous capability is barely isolated at all. A defender inspecting a host reads /proc/PID/ns to see which namespaces a process inhabits and whether it shares the host's; a "containerized" process whose network namespace symlink equals the host's is on the host network directly. The user namespace is the pivotal hardening control, because mapping container root to an unprivileged host UID means a breakout lands as nobody rather than as root. The recurring lesson is that container security is a property of configuration, not of the word "container," and auditing it means reading the actual namespaces, capabilities, and mounts a workload was given.

/tmp, /dev/shm, and world-writable directories

World-writable directories are a normal and necessary part of a Linux system, but they are also the natural staging ground for anything an unprivileged foothold wants to do, so defenders map them deliberately. The obvious ones are /tmp and /var/tmp on disk and /dev/shm in memory, all writable by everyone and all carrying the sticky bit so users cannot delete each other's files. Attackers favor them because a low-privileged process can always write there, and /dev/shm is especially attractive because it is memory-backed, fast, and often overlooked by scans that focus on disk. A defender hunts for other world-writable locations with find / -xdev -type d -perm -0002 2>/dev/null and treats any outside the expected set as a finding, particularly a world-writable directory that sits in the PATH of a privileged job, because that turns into command substitution against a root process. Executable content in these directories is a signal: a compiled binary or a script in /tmp with a recent mtime, especially one currently running per /proc, warrants a look. Hardening reduces the exposure without breaking legitimate use: mounting /tmp, /var/tmp, and /dev/shm with noexec, nosuid, and nodev prevents executing payloads and honoring setuid bits from those mounts, which is a meaningful obstacle even though determined attackers have workarounds. The point of mapping these directories is not that their existence is wrong but that they concentrate opportunity, so they deserve tighter mount options and closer watching than the rest of the tree.

auditd: recording the events that matter

Ordinary logs record what applications choose to report; the Linux audit subsystem records what the kernel observes, which makes auditd the closest thing to a tamper-evident flight recorder a defender can run in place. Rules loaded through auditctl or persisted in /etc/audit/rules.d tell the kernel which syscalls, file accesses, and events to log, and the records land in /var/log/audit/audit.log, queryable with ausearch and summarized with aureport. A proportionate rule set watches the things this corpus keeps returning to: writes to /etc/passwd, /etc/shadow, /etc/sudoers and the sudoers.d directory; execution of privilege tools; changes to authorized_keys and PAM configuration; loading of kernel modules; and use of sensitive syscalls. Well-chosen rules carry a key so events are easy to retrieve later, for instance a rule tagging shadow-file writes so ausearch -k can pull them all. The discipline is in restraint and protection: auditing every syscall drowns the analyst and burdens the host, so rules target high-signal events, and the configuration itself is made immutable at boot with the -e 2 flag so an attacker cannot silently disable auditing without a reboot that itself leaves a trace. As always the records are only trustworthy while the host is; forwarding them to a separate collector in real time preserves evidence even if the host is later compromised, and turns auditd from a local log into durable testimony.

Common misconfigurations and their remediations

Many incidents trace back not to exotic exploits but to a small set of misconfigurations that recur across environments, and a defender who fixes these preemptively removes most easy footholds. World-writable sensitive files: a config, script, or cron job writable by everyone lets any user alter privileged behavior, remediated by tightening ownership and mode and by scanning for the pattern regularly. Overly broad sudo, especially NOPASSWD ALL or grants of shell-capable programs, remediated by narrowing rules to specific, non-escape-capable commands and restoring the password gate. SSH exposed with password authentication and root login enabled, remediated by keys-only authentication, PermitRootLogin no, and source restrictions. Service accounts with login shells and real passwords, remediated by setting nologin shells and locking the password. Secrets in world-readable files, shell histories, or environment, remediated by moving them to restricted stores and rotating anything exposed. Default or weak credentials on local services and databases bound to all interfaces when they should be loopback, remediated by binding to localhost and firewalling. Missing updates on network-facing software, remediated by a patch cadence rather than heroics. The unifying remediation principle is least privilege applied concretely: every account, file, service, and capability should hold exactly the access its function requires and no more, and each item above is that principle violated in a specific, checkable way. The audit is not glamorous, but it closes the doors attackers actually use.

Firewalls, nftables, and reasoning about reachability

A host firewall defines which packets the kernel accepts, and reading it correctly is how a defender learns actual reachability rather than assumed reachability. Modern Linux uses nftables, configured with the nft command and often fronted by a manager like firewalld or ufw, while older systems use iptables; in all cases the kernel evaluates rules in order and the first decisive match wins, so the effective policy is a composition that must be read as a whole, not sampled. A defender lists the ruleset with nft list ruleset and asks, for each listening service found earlier with ss, whether the firewall's exposure matches intent: a service that must be internal should be reachable only from defined ranges, and a default-accept input policy with a few blocks is far weaker than a default-drop policy with explicit allows. The two views must be cross-checked, because a port can listen while being firewalled, and a rule can allow a port on which nothing listens; neither is immediately dangerous, but the first is latent exposure waiting for a rule change and the second is clutter that hides intent. Reachability also depends on layers the host cannot see, cloud security groups, upstream ACLs, and network firewalls, so a host that looks closed locally may be exposed elsewhere or vice versa. The disciplined statement of a firewall audit is therefore conditional: given this ruleset and these listeners, these services are reachable from these sources, pending confirmation of the surrounding network controls that the host itself cannot observe.

A defender auditing nsswitch reads each database line and asks whether every listed source is intended: an unexpected module name after passwd or shadow could route authentication through attacker-controlled code, and because NSS modules are shared libraries loaded into many privileged processes, a malicious one is both stealthy and broadly effective, comparable to a PAM backdoor in reach. The hosts line matters for a different reason: its ordering of files and dns determines whether /etc/hosts can override DNS, which is a legitimate mechanism and also a way to redirect a host's outbound connections by editing a local file. The audit therefore pairs nsswitch.conf with the files it points into, checking /etc/hosts for entries that redirect update servers or internal services, and confirming that any non-file identity source is a sanctioned directory rather than an injected module. As elsewhere, legitimate changes here are infrequent and adversarial changes are severe, so baselining nsswitch.conf and the NSS module set and alerting on drift is a proportionate control for a mechanism that sits underneath both identity and name resolution.

SELinux, AppArmor, and mandatory access control

Standard Linux permissions are discretionary: the owner of a file decides who may access it, and root may do anything, which means a single compromised privileged process faces no further policy barrier. Mandatory access control adds a second, non-discretionary layer that the kernel enforces regardless of ownership, so that even root, or a compromised daemon running as root, is confined to what its security policy permits. SELinux, common on RHEL-family systems, labels every process and object and enforces a policy that says which labeled domains may act on which labeled types; AppArmor, common on Debian and SUSE systems, confines programs by path-based profiles. A defender's interest is twofold. First, these systems contain blast radius: a web server confined by an SELinux domain or an AppArmor profile that only permits its own files and ports cannot, even if exploited, freely read /etc/shadow or write to system directories, so their presence and enforcement is a hardening win to confirm rather than assume. Second, their state is itself an audit target, because attackers and careless administrators disable them: SELinux dropped to permissive or disabled mode with getenforce, an AppArmor profile set to complain instead of enforce, or a policy loosened to grant a domain sweeping access, each removes a layer silently. The audit therefore checks that MAC is enabled and enforcing, that the profiles or policy for exposed services are actually confining and not permissive, and that denials in the audit log, which record exactly the boundary crossings the policy stopped, are being watched, since a sudden change in denial patterns can signal either an attack being blocked or a policy being weakened.

Closing note: composing controls into defense in depth

No single control in this corpus stops a determined adversary, and stating that plainly is the beginning of designing well, because the strength of a hardened Linux host comes not from any one measure but from layering measures so that defeating one still leaves others, and so that the act of defeating each leaves evidence. Consider how the pieces compose. Least privilege shrinks what any compromise can reach, so that breaching a daemon confined to an unprivileged user, a read-only filesystem view, and a minimal capability set yields little. Mandatory access control adds a barrier that even root cannot casually cross. Tightened mount options deny the easy staging of payloads. Keys-only SSH with narrow sudo removes the cheap paths to and from privilege. auditd and off-host logging ensure that the attacker's necessary actions, writing a persistence file, adding a key, loading a module, are recorded somewhere they cannot later erase. File integrity baselines and routine fleet enumeration ensure that whatever the attacker changed to persist becomes a diff a defender will see. Each layer raises cost and lowers stealth, and their combination means an intruder must defeat prevention, evade detection, and resist eradication simultaneously, rather than winning at a single point. The honest framing is not that a well-hardened host is unbreachable, since it is not, but that it is expensive to breach quietly and hard to hold silently, and that when it is breached the defender has both bounded the damage and preserved the evidence needed to understand and reverse it. That is the realistic aim of Linux hardening, defense in depth measured not by the promise of perfect prevention but by the assurance that every layer an attacker must cross makes them slower, poorer, and more visible, which over time is what turns defense from a hope into an advantage.
