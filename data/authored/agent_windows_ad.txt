Windows Security Event 4624 is the anchor of most logon analysis. It records a successful account logon on the machine where the logon occurred. The single most important field is Logon Type, because it distinguishes a person sitting at a keyboard (Type 2, Interactive) from a network share access (Type 3, Network), a scheduled task or service (Type 5, Service), a RemoteInteractive RDP session (Type 10), unlocking a workstation (Type 7), or a batch job (Type 4). Defenders should never read "successful logon" as benign on its own. A Type 3 logon with the NTLM package to a domain controller from a workstation IP, using a highly privileged account at 03:00, is a different story than a Type 2 logon by that user at 09:00 from their assigned desk. Build baselines per account and per logon type. Also capture the Logon ID, a hex value unique to that session on that host, which lets you stitch 4624 to later 4672 (special privileges) and 4634/4647 (logoff) events for the same session. Watch the Elevated Token and Impersonation Level fields when investigating privilege questions.
<<<DOC>>>
Event 4625 is a failed logon and its Status and Sub Status codes carry the real meaning. 0xC000006A means the account name was valid but the password was wrong; 0xC0000064 means the account name itself does not exist; 0xC0000234 means the account is locked out; 0xC0000072 means the account is disabled; 0xC0000193 means the account has expired; 0x0000006F relates to logon-hours restriction. For a defender, the difference between 0xC000006A and 0xC0000064 is the difference between password spraying against real accounts and a mistyped or enumerated username list. A burst of 0xC0000064 across many nonexistent names suggests dictionary username enumeration; a slow drip of 0xC000006A against many valid accounts using one or two common passwords suggests spraying designed to stay under lockout thresholds. Correlate 4625 by source workstation, by source IP, and by the Logon Process and Authentication Package. Kerberos pre-auth failures often surface as 4771 rather than 4625, so do not rely on 4625 alone for a complete failure picture.
<<<DOC>>>
Event 4672, "Special privileges assigned to new logon," fires when a logon session is granted sensitive privileges such as SeDebugPrivilege, SeTcbPrivilege, SeBackupPrivilege, or SeImpersonatePrivilege. In practice, 4672 accompanies almost every administrator or SYSTEM logon, so its value is not that it happens but for whom and where. A useful detection is 4672 for an account that is not expected to hold administrative rights, or 4672 on a host where that account has never before logged on with privilege. Because 4672 shares the Logon ID with the corresponding 4624, you can join them to answer "which privileged session, from which source, at what time." SeBackupPrivilege and SeRestorePrivilege deserve special attention because they permit reading and writing files while bypassing ACLs, a common path to extracting sensitive registry hives. SeDebugPrivilege permits opening arbitrary process handles and is frequently abused to read memory from sensitive processes. Alert when these privileges appear for service or ordinary user accounts outside their documented role.
<<<DOC>>>
Event 4688, "A new process has been created," is one of the most valuable audit events, but only if you enable command-line auditing. Without the "Include command line in process creation events" policy (and the corresponding registry value ProcessCreationIncludeCmdLine_Enabled), 4688 records the image path but not the arguments, which strips away most of the signal. With command lines captured, defenders can reason about parent-child relationships: a spawn of cmd.exe or powershell.exe whose parent is winword.exe or excel.exe is a classic macro-execution pattern; a process whose parent is w3wp.exe (IIS worker) may indicate a web shell. The New Process Name, Creator Process Name, Creator Process ID, and Token Elevation Type fields together let you build process trees. Be careful: command lines can contain credentials or tokens, so 4688 logs themselves become sensitive data that must be access-controlled. Sysmon Event ID 1 provides a richer version of the same idea, adding hashes, the loaded image's signature status, and the original file name from the PE header.
<<<DOC>>>
Kerberos in Active Directory rests on tickets, and two event IDs on domain controllers describe the flow. Event 4768 records a Kerberos authentication ticket (TGT) request: a client proves knowledge of its secret and receives a Ticket Granting Ticket. Event 4769 records a service ticket (TGS) request: the client presents its TGT and asks for a ticket to a specific service, identified by its Service Principal Name. For defenders, 4769 is where Kerberoasting shows up, because requesting a service ticket for an account with a weak password lets an attacker attempt offline cracking of the returned ticket, which is encrypted with the service account's key. The signal is not any single 4769 but an unusual volume of TGS requests for many distinct SPNs from one account in a short window, especially requests specifying the weaker RC4 encryption type (Ticket Encryption Type 0x17) when the environment otherwise uses AES (0x11 or 0x12). Record the Ticket Options, Ticket Encryption Type, and Client Address on every 4769.
<<<DOC>>>
The Ticket Encryption Type field on Kerberos events is a quiet but powerful indicator. AES types (0x11 for AES128, 0x12 for AES256) are the modern default. RC4-HMAC (0x17) and the legacy DES types are weaker and, in a hardened domain, should be rare. An attacker performing Kerberoasting often prefers RC4 because those tickets are faster to crack offline. So a defender who normally sees AES service tickets and suddenly observes a cluster of 0x17 requests for service accounts has a strong lead, provided they have first established the baseline. The caution is that some legacy applications and appliances genuinely require RC4, so you cannot treat every 0x17 as malicious. The remediation path is to inventory which accounts still negotiate RC4, migrate them to AES where possible, set msDS-SupportedEncryptionTypes appropriately, and then treat residual RC4 as an exception list you actively monitor rather than background noise you ignore.
<<<DOC>>>
NTLM remains present in most Windows environments for backward compatibility, and understanding it is a defensive necessity. NTLM is a challenge-response protocol: the server sends a nonce, the client returns a response computed from the user's NT hash, and the server (or the domain controller via Netlogon) validates it. Two properties make NTLM risky. First, it does not authenticate the server to the client by default, enabling relay attacks where an adversary forwards a victim's authentication to a different service. Second, the NT hash is a password-equivalent: possessing it lets an attacker authenticate without knowing the plaintext, which is the basis of pass-the-hash. Defenders should enable NTLM auditing (the "Restrict NTLM" audit policies produce 8004/8003 events on domain controllers and member servers), identify which applications still require NTLM, and progressively restrict or block it. SMB signing and LDAP channel binding and signing are the primary mitigations against relay.
<<<DOC>>>
Pass-the-hash is best understood defensively as a consequence of two facts: NTLM accepts the hash as proof of identity, and Windows caches credential material in the memory of the LSASS process. An attacker who gains administrative rights on one machine can, in principle, extract cached secrets and reuse them elsewhere. The defensive levers are therefore about reducing what is available to steal and where a stolen secret can be replayed. Credential Guard uses virtualization-based security to isolate NTLM hashes and Kerberos ticket-granting-ticket keys in a separate protected process that normal SYSTEM code cannot read. LSASS protection (RunAsPPL) marks LSASS as a protected process, raising the bar for handle access. Administrative tiering ensures that a Tier 0 credential (domain admin) is never exposed on a Tier 2 asset (a workstation), so even a full compromise of the workstation yields no Tier 0 material to replay. None of these alone is sufficient; together they shrink the attack surface substantially.
<<<DOC>>>
LSASS, the Local Security Authority Subsystem Service, is the process that holds and brokers credential material, which makes it the single most targeted process on a Windows host. Defensive monitoring focuses on who opens a handle to lsass.exe and with what access rights. Sysmon Event ID 10 (ProcessAccess) is the workhorse here: an alert on GrantedAccess masks such as 0x1010 or 0x1410 or 0x143a to lsass.exe from an unexpected source process is a high-value detection, because legitimate access to LSASS memory is rare and comes from a known set of processes. Complementary signals include Sysmon Event ID 11 (FileCreate) for a suspicious dump file, and minifilter or EDR telemetry for memory reads. The defense-in-depth measures are RunAsPPL to make LSASS a protected process light, Credential Guard to move the most valuable secrets out of LSASS entirely, and Attack Surface Reduction rules that block credential-stealing behavior. Treat any process dump of LSASS by non-diagnostic tooling as an incident until proven otherwise.

Golden Ticket and Silver Ticket are attacker techniques whose defensive relevance is entirely about detection and about protecting the keys that make them possible. A Golden Ticket is a forged TGT signed with the KRBTGT account's key; possession of that key lets an attacker mint tickets for any user, including nonexistent ones, with arbitrary group membership and lifetime. The correct defensive posture is to assume the KRBTGT key is the crown jewel: rotate it (twice, with a delay between rotations to avoid breaking in-flight tickets) if domain compromise is suspected, and monitor for anomalies such as TGTs with implausibly long lifetimes or tickets referencing accounts that do not exist. A Silver Ticket forges a TGS for a single service using that service account's key, bypassing the domain controller entirely, which makes it stealthier because no 4768/4769 appears on the DC. Silver Ticket detection leans on the target service's own logs and on inconsistencies like a service logon with no corresponding DC ticket request.
<<<DOC>>>
Service Principal Names, or SPNs, map a service instance to the account that runs it, and they are what make Kerberos service tickets addressable. An SPN looks like MSSQLSvc/db01.corp.local:1433 or HTTP/intranet.corp.local. From a defensive standpoint, SPNs matter for two reasons. First, any authenticated domain user can query which accounts have SPNs, which is exactly how an attacker builds a Kerberoasting target list; you cannot easily prevent the enumeration, so you must ensure the underlying accounts have strong, long, random passwords or are Group Managed Service Accounts. Second, SPNs configured on regular user accounts (rather than dedicated service or gMSA accounts) are a red flag, because such accounts often have human-chosen, crackable passwords and sometimes excessive privileges. Regularly audit the servicePrincipalName attribute across the directory, flag SPNs on privileged accounts, and prioritize those for gMSA migration where the platform supports it.
<<<DOC>>>
Group Managed Service Accounts (gMSAs) are a defensive win that is often underused. A gMSA has its password managed automatically by Active Directory, rotated on a schedule (default 30 days), and the plaintext is never known to any human. The password is a long, random value stored as the msDS-ManagedPassword attribute, retrievable only by the hosts explicitly authorized via the PrincipalsAllowedToRetrieveManagedPassword setting. This directly neutralizes several risks: Kerberoasting against a gMSA is pointless because the 240-bit random password will not crack; there are no sticky-note or config-file passwords to leak; and rotation happens without operational pain. Defenders migrating service accounts to gMSAs should verify that only the intended servers can retrieve the managed password, monitor 4662 events for reads of the managed-password attribute from unexpected principals, and confirm the underlying service supports gMSA before cutover. The remaining discipline is to avoid leaving legacy standard service accounts with SPNs behind after migration.
<<<DOC>>>
Administrative tiering is a structural defense against lateral movement and credential theft, and it is more about discipline than technology. The model divides assets into tiers: Tier 0 contains identity infrastructure (domain controllers, the AD database, ADFS, PKI, and the accounts that control them); Tier 1 contains servers and business applications; Tier 2 contains workstations and standard user devices. The rule is that credentials from a higher tier must never be exposed on a lower tier. A domain admin should administer domain controllers only from a dedicated Privileged Access Workstation, never by logging into a helpdesk laptop where that credential would be cached in LSASS and become stealable. Enforcement uses separate admin accounts per tier, logon-restriction GPOs (Deny logon as batch/service/interactively across tiers), and Authentication Policies and Silos that bind privileged accounts to specific hosts. The payoff: compromising a Tier 2 workstation yields only Tier 2 secrets, containing the blast radius.
<<<DOC>>>
Least privilege in Active Directory is easy to state and hard to sustain because privilege accumulates through daily operations. The most abused privileged groups are Domain Admins, Enterprise Admins, Schema Admins, Administrators, Account Operators, Backup Operators, Print Operators, and Server Operators. Backup Operators is frequently overlooked yet dangerous because SeBackupPrivilege lets a member read any file, including the NTDS.dit database on a domain controller. Account Operators can modify many user and group objects. A defensive review should enumerate the actual membership of each of these groups, confirm every member has a documented need, remove standing membership in favor of just-in-time elevation where possible, and monitor 4728/4732/4756 (member added to a security-enabled global/local/universal group) for the sensitive groups. Nested group membership hides real access, so resolve transitive membership, not just direct membership, when you audit.
<<<DOC>>>
Sysmon (System Monitor) extends native Windows auditing with high-fidelity endpoint telemetry, and a well-tuned Sysmon configuration is one of the highest-value, lowest-cost defensive investments. Key event IDs: 1 (process creation with hashes and command line), 3 (network connection), 7 (image/DLL load, useful for detecting unusual DLLs loaded into sensitive processes), 8 (CreateRemoteThread, associated with code injection), 10 (process access, central to LSASS-handle detection), 11 (file create), 12/13/14 (registry operations), 15 (file stream created, capturing the Zone.Identifier for downloaded files), 22 (DNS query), and 23/26 (file delete). The configuration file is where the value lives: an unfiltered Sysmon deployment drowns the SIEM, while a curated config (many teams start from a community baseline and tune) captures the behaviors that matter. Include and exclude rules should be reviewed as the environment changes, and the config itself should be treated as a protected, version-controlled asset.
<<<DOC>>>
PowerShell logging comes in several layers, and defenders should enable more than one because each has blind spots. Module Logging (records pipeline execution details) is configured per module and produces event 4103. Script Block Logging (event 4104 in the Microsoft-Windows-PowerShell/Operational log) captures the actual code executed, including code that was decoded or generated at runtime, which is invaluable against obfuscation because PowerShell logs the deobfuscated block it is about to run. Transcription writes a text record of console input and output to a protected directory. The System-wide Transcript and Script Block Logging together defeat many "fileless" techniques because the code must materialize in the engine to run, and at that moment it can be logged. Attackers respond by trying to disable logging or by using older engines; therefore, defenders should also remove or constrain PowerShell v2 (which lacks these logging capabilities), monitor for 4104 gaps, and alert on attempts to tamper with the logging configuration.

Group Policy Objects (GPOs) are a double-edged sword: they are the mechanism for enforcing security baselines and, if an attacker can modify them, a mechanism for pushing malicious configuration to many machines at once. A GPO links to sites, domains, or organizational units and applies settings to the computers and users under that scope. The defensive concerns are: who can edit each GPO (delegated write permissions are frequently over-broad), whether the SYSVOL share that stores GPO files has appropriate ACLs, and whether any GPO contains risky settings such as adding a rogue account to local Administrators via Restricted Groups, deploying a scheduled task, or changing audit policy. Monitor event 5136 (a directory object was modified) for changes to GPO objects and gPLink attributes, and monitor SYSVOL for file changes. A sudden edit to a widely linked GPO, especially one that pushes a startup script or a new local admin, warrants immediate review. Legacy Group Policy Preferences that stored a cpassword are an old but still-found credential-exposure bug.
<<<DOC>>>
The KRBTGT account is the key to the entire Kerberos trust in a domain, and defenders should treat it accordingly. Its password hash is used to encrypt and sign every TGT the domain issues. Because it is a system account, its password rarely changes on its own, and many domains have KRBTGT passwords that are years old. That staleness matters: if the KRBTGT key is ever compromised, an attacker can forge Golden Tickets until the key is rotated. Best practice is periodic, controlled rotation of the KRBTGT password, performed twice with a gap of at least the maximum ticket lifetime between the two resets so that tickets issued under the previous key can expire gracefully. Doing both resets back to back invalidates active tickets and causes an outage. There is no legitimate interactive logon by KRBTGT, so any 4768/4769 activity that appears to originate from KRBTGT-signed anomalies, or any interactive use, is worth investigating as potential forgery.
<<<DOC>>>
DCSync is a technique in which an actor with sufficient directory rights asks a domain controller to replicate account secrets, effectively impersonating another domain controller to pull password hashes, including the KRBTGT hash. Defensively, the important insight is which permissions enable it: the extended rights "Replicating Directory Changes" (DS-Replication-Get-Changes) and "Replicating Directory Changes All" (DS-Replication-Get-Changes-All) on the domain object. Legitimately, only domain controllers and specific sync accounts (such as Azure AD Connect's) should hold these rights. A defensive audit enumerates every principal granted those extended rights and removes any that are unexpected. Detection focuses on event 4662 (an operation was performed on an object) where the Properties reference the replication GUIDs, originating from a security principal that is not a domain controller. Because a normal member workstation should never request replication, a 4662 replication read from a non-DC source is a strong indicator of DCSync abuse.
<<<DOC>>>
Lateral movement rarely looks like a single dramatic event; it looks like ordinary administrative tools used from unusual places at unusual times. Remote execution via SMB and named pipes (the technique behind many "psexec-style" tools) manifests as a service creation on the target: event 7045 (a service was installed in the system) in the System log, often with a random or oddly named service, and event 4697 (a service was installed, in the Security log when audited). Windows Management Instrumentation lateral movement leaves traces in the Microsoft-Windows-WMI-Activity/Operational log and spawns wmiprvse.exe as a parent of the payload. Remote scheduled tasks show up as 4698 (a scheduled task was created). WinRM/PowerShell Remoting appears as wsmprovhost.exe processes and event 4688 with that image. The common defensive thread is baselining: know which hosts legitimately perform remote administration, from which accounts, and treat remote execution from a workstation to many peers as anomalous.
<<<DOC>>>
Event 4697 and event 7045 both concern service installation, and both are lateral-movement and persistence signals. 7045 lives in the System log and fires for any service installation; 4697 lives in the Security log and requires the "Audit Security System Extension" subcategory to be enabled. Attackers use services for two reasons: to execute code as SYSTEM on a target during lateral movement, and to persist across reboots. Defensive value comes from the details: the service name (random strings, or names impersonating legitimate services with slight misspellings), the binary path (a service pointing at a file in a user-writable or temporary directory, or at cmd.exe/powershell.exe, is suspicious), and the account context. Baseline the set of services that are normally installed across your fleet during patch cycles and software deployments, then alert on service installations that fall outside those change windows or that carry command-interpreter binary paths. Correlate with the 4624/4672 that preceded the installation to identify the responsible session.
<<<DOC>>>
Overpass-the-hash (sometimes called pass-the-key) bridges NTLM and Kerberos: an actor who holds a user's NT hash or AES key uses it to request a legitimate Kerberos TGT, then operates with Kerberos tickets rather than raw NTLM, which can blend in better. The defensive takeaways mirror those for pass-the-hash. Reduce credential exposure so hashes are not sitting in memory to be stolen (Credential Guard, tiering, LSASS protection). Prefer AES over RC4 so that the presence of RC4-based TGT requests (4768 with encryption type 0x17) becomes a meaningful anomaly worth reviewing. Monitor for TGT requests that originate shortly after a suspicious privileged logon or LSASS access event on the same host. As always, no single event is conclusive; the value is in the sequence: LSASS access, followed by a Kerberos TGT request using an unusual encryption type, followed by service-ticket requests to move onward.
<<<DOC>>>
Unconstrained delegation is a legacy Kerberos feature and a serious misconfiguration risk. When a computer or service account is trusted for unconstrained delegation, any user who authenticates to it via Kerberos leaves a copy of their TGT in that server's memory, which the server can then reuse to impersonate the user to any service. If an attacker controls such a server and can coerce a privileged account (or a domain controller's machine account) to authenticate to it, they can capture a TGT that grants sweeping access. Defensively: enumerate all accounts with the TRUSTED_FOR_DELEGATION flag in userAccountControl, treat any unconstrained delegation as an exception requiring justification, and migrate to constrained delegation or resource-based constrained delegation which scope the impersonation to specific services. Mark sensitive accounts as "Account is sensitive and cannot be delegated" (or add them to the Protected Users group) so their tickets are never cached on delegating servers. Domain controllers should be the only unconstrained-delegation objects, and even that deserves scrutiny.
<<<DOC>>>
The Protected Users security group is a defensive control that changes how member accounts authenticate, hardening them against several credential-theft techniques. Members cannot authenticate with NTLM, cannot use DES or RC4 for Kerberos pre-authentication, cannot be delegated (constrained or unconstrained), and do not have credentials cached on machines they log into, and their Kerberos TGTs have a shorter lifetime. This makes Protected Users a strong wrapper for the most sensitive accounts, particularly Tier 0 administrators. The caution is compatibility: because members lose NTLM and weak Kerberos ciphers, any account placed in Protected Users must only ever use Kerberos with AES against modern systems, or authentication will simply fail. Do not bulk-add all admins at once; pilot with a few, confirm their workflows still function, and expand. Combine Protected Users with Authentication Policy Silos to additionally restrict where those accounts can log on from, and with dedicated Privileged Access Workstations.

Password spraying is a low-and-slow credential attack designed to evade account lockout: rather than many passwords against one account, the actor tries one or a few common passwords against many accounts, spaced over time. In event terms it produces a scattering of 4625 failures with status 0xC000006A (bad password on a valid account), or, in cloud/hybrid scenarios, failures at the federation or Azure AD sign-in logs. The detection challenge is that each individual account sees only one or two failures, well under the lockout threshold, so per-account rules miss it. The correct detection aggregates horizontally: count distinct target accounts that failed with the same source, same time window, and same or similar failure code, then alert when one source touches an unusual number of accounts. Defensive hardening includes banned-password lists (blocking seasonal and company-name passwords), MFA, smart lockout that distinguishes familiar from unfamiliar sources, and alerting on authentication from unexpected geographies or ASNs.
<<<DOC>>>
The NTDS.dit file is the Active Directory database on every domain controller, and it contains the password hashes of every account in the domain, including KRBTGT and all administrators. Protecting it is equivalent to protecting the whole domain's credentials. Attackers who reach a domain controller with sufficient rights may attempt to copy NTDS.dit, often using volume shadow copies or backup APIs to read the locked file, which is why SeBackupPrivilege and the Backup Operators group deserve tight control. Defensive monitoring includes watching for shadow-copy creation on domain controllers by unexpected processes, for access to the ntds folder, and for tools that read the SYSTEM registry hive (needed to decrypt the database). Physical and virtual security of domain controllers, encryption of DC backups, restriction of who can log on to DCs at all (ideally only Tier 0 admins from PAWs), and monitoring of any file copy off a DC are the core protections. A leaked DC backup is as catastrophic as a live DC compromise.
<<<DOC>>>
Event 4740 records that a user account was locked out, and it is useful in two opposite directions. As a security signal, a spike in 4740 across many accounts can indicate a spraying or brute-force attempt that is tripping lockout thresholds, or a misconfigured application repeatedly presenting a stale credential. As an operational signal, a single account locking out repeatedly usually points to a cached credential somewhere (a mapped drive, a scheduled task, a mobile device, a service using an old password) rather than an attack. The 4740 event names the Caller Computer Name, which is the machine that submitted the failing authentication, giving you a starting point to trace the source. Correlate 4740 with the preceding 4625 failures to see the status codes and source addresses. For investigation, remember that the lockout is evaluated on the domain controller that holds the PDC emulator role, so lockout events and their timing are best reasoned about with that in mind.
<<<DOC>>>
AdminSDHolder and the SDProp process are AD internals that defenders should understand because they both protect and can betray privileged accounts. AdminSDHolder is a container object whose ACL serves as a template; a background process called SDProp periodically (about hourly) stamps that ACL onto all "protected" accounts and groups (Domain Admins, Enterprise Admins, and other sensitive principals), and sets their adminCount attribute to 1. This protects those accounts from having their ACLs weakened. The security relevance is twofold. First, if an attacker modifies the AdminSDHolder ACL to grant themselves rights, SDProp will happily propagate that backdoor to every protected account, creating stealthy persistence. Second, accounts with adminCount=1 that are no longer actually privileged retain restrictive, inheritance-blocked ACLs, which can confuse later delegation. Defensively, monitor changes to the AdminSDHolder object (5136), review its ACL for unexpected principals, and periodically reconcile adminCount=1 accounts against actual current privilege.
<<<DOC>>>
Constrained delegation and resource-based constrained delegation (RBCD) are the safer successors to unconstrained delegation, but they carry their own abuse potential that defenders must understand. Constrained delegation (via msDS-AllowedToDelegateTo) lets a service impersonate users to a specific list of target services. RBCD (via msDS-AllowedToActOnBehalfOfOtherIdentity, set on the target resource) inverts control so the resource owner decides who may delegate to it. The abuse arises when an attacker who can write the msDS-AllowedToActOnBehalfOfOtherIdentity attribute of a computer object, or who can create a computer account (the default ms-DS-MachineAccountQuota of 10 is often the culprit), configures RBCD to impersonate a privileged user to that machine. Defensive measures: set MachineAccountQuota to 0 so ordinary users cannot join rogue computers, audit write permissions on computer objects' delegation attributes, monitor 5136 changes to msDS-AllowedToActOnBehalfOfOtherIdentity, and restrict who can create or modify computer accounts.
<<<DOC>>>
Event 4662 is a general-purpose audit of operations performed on Active Directory objects, and while it is verbose, it is essential for detecting directory-level attacks. Its power is in the Properties field, which references the specific control access rights or property GUIDs involved. This is how DCSync is detected: a 4662 where the properties include the replication rights GUIDs (for DS-Replication-Get-Changes and its "All" variant), performed by an account that is not a domain controller. It is also how you detect reads of a gMSA managed password (the msDS-ManagedPassword attribute) or reads of the LAPS password attribute by unexpected principals. The practical difficulty is volume and enabling the right SACLs on the objects you care about, because 4662 only fires where auditing is configured on the object's system access control list. A focused approach audits the domain head object and sensitive OUs rather than everything, keeping the signal usable.

Windows Defender Credential Guard is a virtualization-based-security feature that isolates secrets so that even code running as SYSTEM in the normal OS cannot read them. It moves NTLM password hashes, Kerberos TGT session keys, and cached domain credentials into an isolated LSA process (LSAIso) protected by the hypervisor. The defensive effect is that pass-the-hash and pass-the-ticket become much harder, because the raw hashes and ticket keys are no longer readable from LSASS memory. Its limitations are worth stating honestly: Credential Guard protects derived credentials in memory, not the plaintext at the moment of entry, and it does not protect against keyloggers, does not stop attacks that operate through legitimate authentication (like Kerberoasting or abusing delegation), and requires modern hardware (UEFI, Secure Boot, virtualization extensions) plus incompatibility checks with some VPN and third-party authentication providers. It is a strong layer, not a panacea, and it composes best with tiering, LSASS PPL, and reduced NTLM usage.

Sysmon Event ID 10 (ProcessAccess) is the backbone of credential-dumping detection, and understanding the GrantedAccess field is what separates a noisy rule from a useful one. When one process opens a handle to another, the requested access mask is recorded. Reading another process's memory requires rights such as PROCESS_VM_READ (0x0010) and PROCESS_QUERY_INFORMATION (0x0400); credential-dumping tools historically requested masks like 0x1010, 0x1410, or 0x143a against lsass.exe. The detection strategy is to alert when the target image is lsass.exe and the source is not on an allowlist of legitimate accessors (some AV/EDR, certain diagnostic tools, and Windows Error Reporting under specific conditions). Because attackers can request lower access masks or use cloned handles to evade a naive mask match, the more robust approach combines the target (LSASS), an unexpected source process, and corroborating signals like a subsequent file write of a dump. Maintain and tune the accessor allowlist as legitimate tools change.
<<<DOC>>>
LAPS, the Local Administrator Password Solution, addresses a pervasive weakness: identical or shared local Administrator passwords across many machines, which let an attacker who cracks or dumps one local admin hash move laterally to every machine sharing it. LAPS randomizes each machine's local administrator password, stores it in a confidential AD attribute, and rotates it on a schedule. The Windows LAPS generation (built into modern Windows) can store the password in Active Directory or in Entra ID and supports encryption of the stored value. Defensively, LAPS both hardens (no more password reuse) and requires its own monitoring: reads of the LAPS password attribute are directory operations that should be audited (4662 on the relevant attribute), because an attacker who can read many machines' LAPS passwords gains broad local access. Restrict who can read the attribute to a small, justified set, and alert on bulk reads. Verify rotation is actually occurring and that no legacy shared local admin remains enabled alongside LAPS.
<<<DOC>>>
Detecting lateral movement benefits enormously from thinking in terms of authentication graphs rather than isolated events. Every 4624 on a destination host has a corresponding record of a source. If you collect logons across the fleet and model them as edges (source account, source host, destination host, logon type, time), normal activity forms stable patterns: users log into their own workstation and a handful of servers; admins touch a defined set of infrastructure. Lateral movement appears as new edges: an account suddenly authenticating to hosts it has never touched, a workstation initiating Type 3 logons to many peers, or an admin credential appearing on a machine outside its usual tier. This graph view also surfaces "credential spread," where one compromised account's presence fans out over hours. Tools differ, but the principle is durable: baseline the normal graph, then alert on structurally novel edges, weighting by the sensitivity of the account and destination. Pair this with the service-install and remote-execution signals to confirm the mechanism of movement.

Honeytokens and deception accounts are a low-noise detection strategy that fits AD well. The idea is to plant credentials or objects that no legitimate process should ever touch, so any interaction is inherently suspicious. Examples include a decoy service account with an attractive-looking SPN and a deliberately weak-looking but monitored configuration, whose only purpose is to generate a 4769 when someone Kerberoasts it; a fake set of credentials seeded into memory or a config file that, if used, triggers a 4625 or 4624 from an unexpected source; or a canary AD object with auditing on its read so any enumeration lights up a 4662. The strength of deception is its very low false-positive rate: unlike behavioral rules, a honeytoken has no legitimate use, so an alert is almost always meaningful. The discipline required is to document the deception thoroughly (so responders are not themselves fooled), to keep it realistic enough to be discovered, and to ensure the monitoring on it actually fires and routes to the SOC.

Time synchronization matters more to AD security than it first appears, because Kerberos depends on it. By default, Kerberos allows only a small clock skew (five minutes) between client and domain controller; tickets carry timestamps, and excessive skew causes authentication to fail. From a defensive standpoint, reliable time is what makes cross-host log correlation trustworthy: if endpoints and domain controllers disagree on time, your reconstruction of an incident timeline becomes unreliable, and sequence-based detections (LSASS access, then TGT request, then service tickets) can be scrambled. Ensure the PDC emulator is synced to a trustworthy external source and that the domain hierarchy syncs to it, monitor for hosts whose clocks drift, and record whether your log timestamps are local or UTC so you do not misread an attack window by a timezone offset. When ingesting logs into a SIEM, normalize to UTC. An attacker manipulating time on a host to break correlation or ticket validity is itself a signal worth watching.

Event 4776 is generated on the authenticating authority (a domain controller for domain accounts, or the local machine for local accounts) when credentials are validated using NTLM, specifically "The computer attempted to validate the credentials for an account." Its Error Code field indicates success (0x0) or the reason for failure, and the Source Workstation field names where the attempt originated. For defenders, 4776 is a complement to 4624/4625 because it captures NTLM validations that may not be obvious elsewhere, and it is central to detecting NTLM-based password spraying and pass-the-hash reuse. A cluster of 4776 failures from one Source Workstation against many accounts is a spraying indicator; 4776 successes for an administrative account from a workstation where that admin should never authenticate via NTLM is a pass-the-hash indicator. Because 4776 signals NTLM specifically, tracking its volume also helps you measure NTLM usage as you work to reduce and eventually restrict the protocol.
<<<DOC>>>
An honest account of detection limits keeps defenders effective. First, absence of an event is not absence of activity: if command-line auditing or Sysmon was not enabled, or if logs were cleared (watch for 1102, "the audit log was cleared," and 104 for the System log), the lack of a matching event proves nothing. Second, many detections rest on baselines, and a baseline built during a period that already contained compromise will treat malicious activity as normal. Third, attackers living off the land use legitimate binaries (the "LOLBins") and legitimate protocols, so a single event is almost never conclusive; confidence comes from sequences and context. Fourth, encrypted and signed traffic hides content, so network detection often sees metadata, not payloads. The defensive response to all of this is layering: enable rich logging before you need it, protect the logs from tampering, correlate across host and network and identity, and express findings with calibrated uncertainty rather than false precision.

Event 1102 in the Security log means the audit log was cleared, and it deserves a high-priority alert because clearing logs is both a legitimate rare administrative action and a classic anti-forensic move. The event records the account that performed the clear. Attackers clear logs to destroy evidence of their earlier activity, so a 1102 that is not tied to a documented maintenance action should be treated as suspicious, and it should prompt a pivot to any forwarded copies of the logs. This is precisely why log forwarding matters: if events are shipped to a SIEM or Windows Event Collector in near-real-time, clearing the local log does not erase the centralized record, and the gap between the last forwarded event and the 1102 helps bound what the attacker may have tried to hide. Related events include System log 104 (log file cleared) and, on the collector side, gaps in expected heartbeat events. Protect log-forwarding configuration and the collector itself as high-value assets.

Organizational Units and delegation are where AD's flexibility quietly becomes risk. Administrators delegate control over OUs so that, for example, a helpdesk team can reset passwords for users in a regional OU. Over years, these delegations accumulate, are rarely reviewed, and sometimes grant far more than intended, such as write access to all properties (which can include group membership or userAccountControl) rather than just password reset. The defensive practice is periodic delegation review: enumerate the access control entries on each OU, resolve which principals can do what, and reconcile against documented intent. Pay special attention to any delegation that permits writing sensitive attributes (servicePrincipalName, msDS-AllowedToActOnBehalfOfOtherIdentity, userAccountControl, member) or resetting privileged accounts. Nested and inherited ACEs make this harder than it looks, so use tooling that resolves effective permissions. Monitor 5136 for ACL changes on OUs. Least privilege at the OU level directly limits how far a single compromised helpdesk account can reach.

The concept of "assume breach" reframes AD defense productively. Rather than betting everything on prevention at the perimeter, assume an attacker will eventually get code execution on some endpoint, and design so that this initial foothold does not automatically become domain dominance. Concretely, this means: tier your administration so a workstation compromise yields no Tier 0 credentials; enable rich endpoint and identity logging so the foothold is detectable as it tries to expand; segment the network so lateral movement meets friction; and rehearse response so containment is fast. Assume-breach also changes metrics: instead of only counting blocked attacks, you measure detection coverage (which techniques would you catch), dwell-time reduction, and blast-radius containment. It is not defeatism; it is acknowledging that prevention is imperfect and that the interesting security work is limiting what a foothold can become. Every hardening item in AD (Protected Users, gMSA, LAPS, Credential Guard, tiering) is more valuable when evaluated by how much it shrinks the post-breach blast radius.

Event 4738 ("a user account was changed") and its siblings 4720 (account created), 4722 (enabled), 4725 (disabled), 4723/4724 (password change/reset), 4726 (deleted), and 4767 (unlocked) form the account-lifecycle audit trail. Defensively, these are how you catch persistence and privilege manipulation at the identity layer. A newly created account (4720) that is quickly added to a privileged group (4728/4732) and given a never-expiring password is a common persistence pattern. A 4724 password reset of a privileged account performed by an unexpected operator can indicate account takeover. A 4738 that changes userAccountControl to disable pre-authentication, enable a smart-card-not-required flag, or set "password not required" weakens the account. The practice is to alert on sensitive changes: creation and enabling of accounts outside HR-driven provisioning, group additions to Tier 0 groups, and any userAccountControl change that reduces security. Correlate the operator's session (via Logon ID and the subject fields) to determine who acted and from where.

AS-REP roasting targets accounts configured with "Do not require Kerberos pre-authentication" (the DONT_REQ_PREAUTH flag in userAccountControl). Normally, pre-authentication forces a client to prove knowledge of its password before the domain controller issues an AS-REP, which prevents an attacker from harvesting crackable material for arbitrary accounts. When pre-auth is disabled, anyone can request an AS-REP for that account and receive data encrypted with the account's key, which can be attacked offline. The defensive posture is straightforward: enumerate every account with DONT_REQ_PREAUTH set, treat each as an exception requiring justification, and remove the flag wherever a legacy requirement cannot be proven. For accounts that genuinely must keep it, ensure a long random password (ideally a gMSA) so offline cracking is infeasible, and monitor 4768 requests for those accounts, watching especially for RC4 (0x17) encryption in the responses. This is one of the cheapest AD hardening wins because the misconfiguration is rare and easy to enumerate.
<<<DOC>>>
Windows Event Forwarding (WEF) and a Windows Event Collector give defenders a tamper-resistant, centralized view without deploying a heavy agent everywhere, and configuring it well is foundational. WEF pushes selected events from source machines to a collector over an authenticated channel, using subscriptions that define which events to gather. The defensive advantages are that logs leave the endpoint quickly (so an attacker who later clears local logs cannot erase the forwarded copy), that collection is centralized for correlation, and that the collector can be placed in a more protected tier. Design considerations include curating subscriptions so you gather high-value events (the 46xx logon and privilege events, 4688 with command lines, service installs, PowerShell 4104, Sysmon) without overwhelming bandwidth, securing the collector as a sensitive asset, and monitoring the health of forwarding itself (a source that goes silent may be offline or may have had forwarding disabled by an attacker). Treat gaps in expected forwarding as investigable events, not mere noise.
<<<DOC>>>
Trust relationships between domains and forests extend authentication across boundaries, and they extend risk with it. A trust lets principals in one domain be authenticated by another; the direction and transitivity of the trust determine who can access what. Security-relevant properties include whether SID filtering (SID history quarantining) is enabled, because without it, a compromised trusted domain could inject SIDs into authentication data to claim privileges in the trusting domain. Selective authentication can restrict which principals from the trusted domain may authenticate to which resources. Defensive review of trusts asks: is each trust still necessary; is it transitive when it need not be; is SID filtering enabled on external and forest trusts; and are the domain controllers on both sides at an equivalent security posture, since the trusting domain inherits risk from the least-secure trusted domain. Because a trust makes the security of two environments interdependent, any acquisition or partner integration that introduces a trust warrants a full posture assessment of the far side.

Privileged Access Workstations (PAWs) are dedicated, hardened machines from which administrators perform sensitive work, and they are the practical enforcement point for tiering. The premise is simple: a domain administrator's credential must never be typed into, or cached on, a general-purpose machine that browses the web and reads email, because that machine's larger attack surface would expose the credential. A PAW is locked down: minimal software, no email or general browsing, application allowlisting, restricted network paths that can reach only management interfaces, and often its own administrative tier that ordinary IT cannot touch. Combined with Authentication Policy Silos, you can bind Tier 0 accounts so they can only authenticate from PAWs, meaning a stolen Tier 0 credential is useless from anywhere else. The organizational challenge is adoption: PAWs add friction, and admins route around friction, so successful programs pair the technical control with clear workflows and executive backing. Monitor for Tier 0 logons that originate from non-PAW hosts as a policy-violation and possible-compromise signal.

Coerced authentication techniques trick a target machine, often a domain controller or a privileged server, into authenticating to an attacker-chosen destination, which the attacker can then relay or capture. Several Windows RPC interfaces historically could be abused to prompt a machine account to authenticate outward. The defensive relevance is that machine-account authentications carry the machine's own privileges, and a coerced domain-controller authentication combined with an NTLM relay to a service like AD CS or LDAP can be devastating. Mitigations focus on the relay side and the coercion side together: enforce SMB signing and LDAP signing and channel binding so relays fail; disable NTLM where feasible; patch the RPC interfaces that permit coercion; and restrict which hosts can reach the vulnerable RPC endpoints on sensitive servers. On the detection side, watch for machine accounts authenticating to unexpected internal hosts, and for NTLM authentications to services that should only ever see Kerberos. As always, the presence of one indicator invites investigation, not conclusion.

Active Directory Certificate Services (AD CS) is part of the identity trust fabric, and misconfigured certificate templates have become a significant escalation path, so defenders need a working model of the risks. A certificate that permits client authentication effectively is a credential; if a low-privileged user can enroll for a certificate that identifies them as someone else, or that can be used to authenticate as a privileged account, that is a direct escalation. Risky template conditions include allowing the enrollee to supply the subject (subjectAltName) while also enabling client authentication, overly broad enrollment permissions, and enrollment agents that can request on behalf of others. Defensive review enumerates every template, its Extended Key Usages, who may enroll, and whether the CA allows requester-supplied subjects. Monitor certificate issuance (the CA logs and event 4886/4887 for request and issue) for anomalies such as a low-privileged account obtaining a certificate mapped to a privileged identity. Harden by removing dangerous template flags, tightening enrollment ACLs, and enabling strong certificate mapping so a certificate cannot be repurposed to impersonate.

Baseline building is the unglamorous foundation under most AD detection, and doing it deliberately pays off. A useful baseline captures, per account and per host: normal logon types and hours, the set of hosts each account authenticates to, which service accounts request which SPNs and how often, the normal rate and encryption types of Kerberos tickets, the set of services installed during change windows, and the parent-child process patterns of common applications. The point of a baseline is to make anomalies computable: "this account requested 40 service tickets when it has never requested more than 2" is only a detection if you know the "never more than 2." Two cautions keep baselines honest. First, seed them from a period you have reason to believe is clean, or you will normalize existing intrusion. Second, baselines drift as the business changes, so schedule periodic recalibration and treat large baseline shifts as themselves worth a glance. Detection maturity is largely a story of ever-better baselines feeding ever-more-specific anomaly rules.

A calm word on alert fatigue and calibration closes the loop on all of this. Every detection discussed here, from LSASS-handle access to Kerberoasting bursts to novel authentication edges, will occasionally fire on legitimate activity: a backup agent that reads protected files, an administrator legitimately touching many servers during maintenance, a security scanner that enumerates SPNs. If a SOC treats every fire as an incident, analysts burn out and real signals drown. The defensive craft is calibration: tune each rule against a known-good baseline, attach context (is this account privileged, is this host Tier 0, is there a change ticket) so alerts arrive pre-enriched, and express confidence honestly so a low-confidence anomaly is triaged differently from a high-confidence chain of corroborating events. Suppression must be principled, not lazy: document why an exception exists and review it, because today's benign backup account is tomorrow's compromised one. The goal is not zero alerts nor infinite alerts, but a stream of well-contextualized, appropriately-uncertain signals that a human can reason about and act on with approval.

Machine accounts (the computer objects ending in $) authenticate and hold privileges just like user accounts, and defenders sometimes forget them. A domain controller's machine account, for instance, is effectively as powerful as a domain admin for many purposes, and any server's machine account can be a lateral-movement vehicle if its secret is captured. Machine account passwords rotate automatically by default (roughly every 30 days) and are long and random, which is good, but the account still authenticates constantly, so its behavior can be baselined. Anomalies worth watching include a machine account authenticating interactively (unusual), a machine account being used from a host other than itself, or an unexpected reset of a machine account password (which can be part of certain takeover techniques against computer objects). Because coerced-authentication techniques weaponize machine-account authentications, and because RBCD abuse manipulates computer-object attributes, treating computer objects as first-class security principals, with their own baselines and their own attribute-change monitoring (5136 on delegation attributes), closes a gap that user-centric monitoring leaves open.

Finally, a synthesis of how these pieces compose into a defensible domain. Prevention narrows the entry: patching, MFA on remote access, phishing-resistant authentication, banned passwords, and disabled legacy protocols. Hardening shrinks what a foothold becomes: tiering with PAWs and Authentication Silos, Protected Users for sensitive accounts, gMSAs and LAPS to eliminate reusable and shared credentials, Credential Guard and LSASS PPL to protect in-memory secrets, MachineAccountQuota set to zero, and disciplined delegation with no unnecessary unconstrained delegation. Detection assumes breach: rich logging (command-line 4688, Sysmon, PowerShell 4104) forwarded off-host to a protected collector, baselines that make anomalies computable, and correlation across identity, endpoint, and network so that sequences (LSASS access, then anomalous TGT, then fan-out logons, then service installs) raise confidence. Response contains the blast radius quickly: isolation, credential resets scoped correctly, and KRBTGT rotation when domain compromise is suspected. No single control is decisive; security is the product of overlapping, honestly-monitored layers, each reducing the probability that an ordinary foothold becomes an extraordinary loss.
