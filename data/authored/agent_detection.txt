EXPLAINER: A detection as a testable hypothesis

A detection rule is not a fact; it is a hypothesis about telemetry. The disciplined form is: "If adversary behavior B occurs, then observable O will appear in data source D within window W, and O is rare among benign activity." Writing the rule this way forces you to name every assumption. Consider credential dumping from LSASS memory (T1003.001). The hypothesis is: a process that is not a known security agent opens a handle to lsass.exe with access mask granting read of process memory, and this is uncommon on standard endpoints.

Data source: EDR process-access events (Sysmon Event ID 10 or the vendor equivalent), which record SourceImage, TargetImage, and GrantedAccess.

Logic in pseudocode:
  where TargetImage endswith "lsass.exe"
  and GrantedAccess in {0x1010, 0x1410, 0x1438, 0x143a, 0x1fffff}
  and SourceImage not in allowlist(known_av, edr, backup_agents)
  then raise candidate

Expected false positives: legitimate security products, some backup and DLP agents, Windows Defender, and occasionally crash-handling tools (WerFault). Enterprise monitoring suites also read process memory.

Validation on labeled telemetry: assemble a set of confirmed benign days from a representative sample of endpoints, run the logic, and count how many distinct source images trigger. Each recurring benign source becomes an allowlist candidate. Then replay a red-team exercise or purple-team run where LSASS access was performed, and confirm the rule fires. Precision is estimated as true positives over all alerts on the benign+attack corpus; recall is the fraction of known attack instances caught. Report both, with the sample sizes, because a rule that fires once per day per endpoint is not deployable regardless of recall.

EXPLAINER: Precision, recall, and why base rates dominate

Detection engineers report two numbers that are easy to conflate. Recall (sensitivity) is the fraction of true malicious events the rule catches. Precision is the fraction of alerts that are truly malicious. In security the base rate of malice is tiny, so precision is punishing. Suppose a rule has recall 0.90 and a false-positive rate of 0.1 percent against benign events. On a network generating one million relevant benign events per day and, say, ten true malicious events, the rule produces roughly 1000 false alerts and 9 true ones. Precision is about 0.9 percent. That rule is undeployable as a page-the-analyst alert even though its recall looks excellent.

The lesson: for high-volume data sources, a false-positive rate that sounds negligible in percentage terms still floods the queue because it multiplies against an enormous denominator. Engineers respond by (1) narrowing the population the rule examines, (2) requiring a conjunction of independent observables so the joint false-positive rate collapses, or (3) routing low-precision-but-useful signals to enrichment or risk-scoring pipelines rather than to a human. Always compute the expected daily alert count, not just the rate, before shipping.

EXPLAINER: False-positive profiles as first-class artifacts

A detection without a documented false-positive profile is unfinished. The false-positive profile enumerates the benign behaviors that look like the malicious one, why they collide, and how a tuner should tell them apart. For a rule on encoded PowerShell (T1059.001, -EncodedCommand usage), the profile might read: "Benign collisions include Microsoft management tooling, some software installers, and legitimate admin scripts that base64 a payload to avoid quoting problems. Distinguishers: the decoded content, the parent process, the signing status of the initiating binary, and whether the invocation originates from an interactive session versus a service."

Writing this profile is what converts an alert into something an analyst can adjudicate in seconds. It also seeds automated enrichment: if the profile says "decode the payload and check for download cradles," that becomes an enrichment step. The profile is a living document; every confirmed false positive should either be explained by an existing entry or add a new one. When the profile stops growing, the rule has matured.

EXPLAINER: Detection as code and the review pipeline

Treating detections as code means each rule is a versioned file with metadata, tests, and a review history, managed the same way as application source. A rule file carries: a stable id, the ATT&CK technique(s) it addresses, the data source and required fields, the logic, the false-positive profile, severity, and at least one unit test consisting of a synthetic event that must match and one that must not. A continuous integration job parses every rule, validates the schema, runs the tests against fixtures, and rejects a merge if a rule references a field absent from the data-source schema.

This discipline yields several benefits. Changes are reviewable: a peer can see that a threshold moved from 10 to 50 and ask why. Regressions are caught: if someone edits a shared macro and breaks twelve rules, the test suite fails. Coverage is measurable: a script can roll up which techniques have at least one tested rule. And rollback is trivial. The cultural shift is that a detection is never "done in the console"; it is proposed as a change, reviewed, tested, and merged, exactly like a bug fix.

EXPLAINER: Threshold selection from the benign distribution

Thresholds should be derived, not guessed. When a detection counts something (failed logons, DNS queries to distinct subdomains, bytes egressed), the right threshold comes from the benign distribution of that count. The procedure: gather a representative window of known-benign telemetry, compute the per-entity distribution of the metric, and place the threshold well into the tail. If benign hosts issue at most 40 distinct NXDOMAIN lookups per hour at the 99.9th percentile, a DNS-tunneling heuristic (T1071.004) might trigger at, say, 150 to leave headroom and avoid seasonal drift.

Two cautions. First, distributions differ by population; servers, developer workstations, and kiosks each have their own baseline, so segment before you threshold. Second, thresholds decay. A value chosen against last quarter's traffic may be wrong after a new application deploys. Record the percentile you targeted and the date, and schedule a periodic recomputation. A threshold with a documented derivation can be defended in review; a round number with no provenance cannot.

EXPLAINER: Correlation rules and independence

Single-signal detections are noisy; correlation rules combine signals so the joint false-positive rate falls. The key assumption is independence: if two observables are statistically independent among benign activity, the probability both appear by chance is the product of their individual rates. A rule that fires on "new service installed" (T1543.003) alone may be noisy because software installs services routinely. A rule that fires on "new service installed AND the service binary is unsigned AND it was created within five minutes of a suspicious parent process" is far more precise, because those conditions rarely coincide in benign operations.

The trap is correlated correlates. If your two signals actually measure the same underlying benign cause, combining them buys little. Antivirus updates might both install services and drop unsigned helper binaries, so on that population the signals are not independent and the conjunction still fires. Validate correlation rules the same way as single rules: measure the joint alert volume on benign telemetry, do not assume the math. Correlation also introduces windowing questions, addressed separately, and state cost, since the engine must hold partial matches in memory.

EXPLAINER: Mapping coverage to MITRE ATT&CK honestly

A coverage map answers "which adversary techniques can we detect, and how well?" The honest version avoids two failure modes: claiming a technique is covered because one rule mentions it, and claiming a red heatmap cell means real protection. Coverage has depth. A single brittle rule keyed on one tool's default artifact is thin; multiple rules spanning distinct data sources and sub-behaviors is robust. Encode this: for each technique, record the number of rules, the diversity of data sources, and an assessed confidence (validated by test / validated by purple team / theoretical).

Also record procedure-level nuance. ATT&CK techniques are broad; a technique like T1055 (process injection) has many procedures, and a rule catching CreateRemoteThread does nothing against a procedure using thread hijacking or mapped sections. So a technique should not be painted "covered" without noting which procedures. The output is not a comforting all-green wall but an inventory of what you can and cannot see, with the gaps named. That inventory drives the detection backlog: prioritize techniques that are both high-likelihood for your threat model and currently thin or untested.

EXPLAINER: The difference between EDR and SIEM signals

EDR and SIEM answer different questions and fail differently. EDR sits on the endpoint and sees rich local context: process trees, memory access, image loads, in-memory reflection, API telemetry. It is excellent for behavioral detection at the host but blind to activity on unmanaged devices and can be evaded or disabled by an attacker with sufficient privilege. SIEM aggregates logs from many sources: firewalls, proxies, identity providers, cloud control planes, and the EDR itself. It sees breadth and cross-host correlation but at lower fidelity and higher latency, and it inherits every collection gap.

Good detection engineering uses both deliberately. Host behavioral logic belongs where the context is richest, on the EDR. Cross-domain correlation such as "impossible travel followed by mailbox rule creation" belongs in the SIEM because no single endpoint sees it. A subtle point: the EDR is also a SIEM data source, so a detection can live in the SIEM keyed on EDR events when you need to correlate them with identity or network data. Deciding placement is an engineering choice about latency, context, retention, and the blast radius if that layer is blind.

EXPLAINER: Sigma-style reasoning without vendor lock-in

A portable detection is expressed as logic over normalized fields, not as one product's query syntax. The reasoning pattern, in the spirit of Sigma, is: name the log source category (for example, process_creation on Windows), state the selection (field-value conditions that must hold), state any filter (benign conditions to exclude), and define the condition as selection AND NOT filter. Keeping this in an abstract form means the same intent can be compiled to different backends and, crucially, reviewed for correctness independent of query dialect.

For instance, a portable detection for suspicious use of certutil to download a file (an abuse of a signed system binary, T1105 ingress transfer) reasons: selection is image ends with certutil.exe and command line contains a URL-fetch verb and an http reference; filter excludes known internal update URLs and approved admin hosts; condition is selection and not filter. Written this way, a reviewer can debate whether the verb list is complete and whether the internal-URL filter is too broad, without being distracted by syntax. The abstract rule is also testable against synthetic events regardless of the platform it ultimately runs on.

EXPLAINER: Alert quality metrics you can actually track

Alert quality is measurable if you instrument dispositions. Track, per rule and per week: alert volume, true-positive count, benign/false-positive count, and unresolved count. From these derive precision (true positives over adjudicated alerts) and a workload figure (alerts per analyst-day). Add time-to-triage as a latency metric. A rule whose precision drops below a target for two consecutive periods enters a tuning queue; a rule that has produced zero true positives in a long window and cannot be justified by rarity of the threat is a candidate for retirement or downgrade to enrichment.

Recall is harder because you rarely know what you missed. Approximate it with purple-team exercises and with post-incident reviews that ask, for every confirmed incident, "which rules should have fired, and did they?" Every missed detection during a real incident is a recall data point and should generate either a new rule or a documented reason the miss was acceptable. Publishing these metrics changes behavior: engineers stop shipping vanity rules and start defending precision, and leadership sees coverage as a maintained asset rather than a one-time project.

EXPLAINER: Rare-by-design detections and the first-seen pattern

Some of the most durable detections are not signatures but rarity tests. The pattern is "first seen": maintain a baseline of what has been observed for an entity, and alert when something appears for the first time in a meaningful context. Examples: a user authenticating to a system they have never touched, a host beaconing to a domain never before contacted by the organization, a service account suddenly running an interactive shell, or a parent-child process pair never previously seen on the fleet.

First-seen detections resist evasion because they do not depend on a specific tool artifact; they depend on the behavior being novel. Their weakness is cold start and churn. On day one everything is new, so you need a warm-up period during which you learn the baseline without alerting. And environments change: new software, new employees, new partners generate legitimate novelty. The engineering answer is to scope tightly (first-seen for privileged accounts only, or first-seen destinations for servers that normally talk to a fixed set of endpoints) so the novelty that remains is genuinely suspicious. Always pair a first-seen rule with the enrichment that lets a human judge whether the novelty is benign onboarding or an intrusion.

EXPLAINER: Log source health as a detection dependency

A detection is only as alive as the log it reads. Silent log-source failure is a leading cause of undetected intrusions: the rule is fine, but the data stopped arriving. Therefore monitor the pipeline itself. For each critical source, track expected event volume per unit time per host and alert when volume drops sharply or goes to zero, which can indicate agent failure, a tampering attempt (T1562, impair defenses), or a misconfigured forwarder. Heartbeats and volume baselines are detections about your detections.

Design these health checks with the same rigor as any rule. A naive "alert if zero events in the last hour" fails on legitimately quiet hosts overnight. Segment by host role and time-of-day, and compare against the entity's own recent baseline. Also watch for the subtler failure where events still flow but a critical field has gone empty because an auditing policy changed; a rule keyed on that field now has zero recall while appearing healthy. Field-level population checks catch this. Treat the observation "we could not have detected this because the log was missing" as a serious finding in every post-incident review.

EXPLAINER: Writing the falsifiable version of an alert

Analysts triage faster when an alert states not just "this looks bad" but "here is what would prove me wrong." Bake a falsification path into the detection's runbook. For a beaconing detection (regular-interval C2, T1071), the falsifiers are: the destination is a known software-update or telemetry endpoint; the regularity is a scheduled task or monitoring poll; the process is a signed, high-prevalence binary with a legitimate reason to poll. Listing these turns triage into a checklist rather than an open-ended investigation.

The habit also improves the rule. If you cannot articulate what benign cause would produce the same signal, you probably have not characterized your false positives, and the rule will surprise you in production. Falsifiers should be phrased as concrete, checkable queries: "pull the destination's category and first-seen date," "check whether the interval matches a known scheduled task," "confirm the binary's fleet prevalence." When the falsifiers are all checked and none holds, confidence is earned rather than assumed, and the escalation carries the evidence with it.

EXPLAINER: Beaconing detection by timing regularity

Command-and-control channels often beacon at regular intervals, and that regularity is detectable even when the payload is encrypted and the destination is unknown. The hypothesis: malicious beacons produce connections whose inter-arrival times cluster tightly around a period, sometimes with jitter, in a way that differs from human-driven or bursty application traffic. Data source: network flow or proxy logs with per-connection timestamps grouped by (source host, destination). Logic: for each host-destination pair over a window, compute the inter-arrival intervals and a regularity measure such as low variance relative to the mean, or a strong peak in the interval histogram, above a minimum connection count.

Expected false positives are substantial and specific: software update checks, telemetry and analytics beacons, monitoring agents, NTP, certificate-status polling, and chat or presence keepalives. All of these are regular by design. The distinguishers are destination reputation and age, process prevalence, and whether the destination is on a known-good list. Validate by first characterizing your environment's benign periodic talkers (there are many), allowlisting them, and then replaying a controlled beacon from a lab implant to confirm detection at various jitter settings. Report the recall at each jitter level, because heavy jitter degrades timing-based detection and you should know where your blind spot begins.

EXPLAINER: Detecting living-off-the-land abuse

Attackers increasingly avoid custom malware and instead abuse legitimate, signed system utilities, so-called living-off-the-land binaries, to blend in. Because the binaries themselves are trusted, detection must key on anomalous usage rather than presence. The hypothesis form is: utility U is being invoked with arguments, by a parent, from a path, or by an account that is uncharacteristic of its benign use. For example, a scripting or archive utility spawned by a document-viewer process, or a signed binary invoked with a network-download argument by a user who never administers systems.

Data sources are process-creation logs with command lines and parent-child lineage, plus image-load telemetry for cases where the abuse is a DLL side-load. The logic focuses on context: parent process, command-line intent verbs, invoking account role, and destination. Expected false positives are heavy because these utilities have legitimate administrative uses; the false-positive profile must enumerate which admin roles and automation legitimately use them. Validate by baselining each utility's benign invocation profile across the fleet, then testing against known abuse procedures. The durable insight is that you are modeling normal usage of trusted tools and alerting on the tail, which requires good baselines and continuous maintenance as legitimate usage evolves.

EXPLAINER: Detecting defense evasion via log tampering

Sophisticated intruders attempt to blind defenders by clearing logs, stopping agents, or altering audit policy (T1562, T1070). Detecting this requires treating the security telemetry pipeline as a monitored asset in its own right. Hypotheses include: the Windows event log service is stopped or the Security log is cleared (event 1102 is itself an indicator, if it still reaches you); an EDR agent process terminates outside of a sanctioned update; audit policy is modified to disable categories; or telemetry volume from a host collapses while the host remains reachable.

The paradox is that the very act being detected may suppress the evidence of it, so you must catch the signal before it is silenced or infer it from absence. Absence-based detection, alerting on the unexpected quiet, is powerful here but requires reliable per-entity volume baselines to avoid false alarms on legitimately idle hosts. Corroborate with independent vantage points: a network sensor still sees a host that has blinded its own endpoint agent. Expected false positives include legitimate agent upgrades, imaging and decommissioning, and sanctioned maintenance, all of which should be represented in change records so the detection can distinguish planned quiet from imposed quiet.

EXPLAINER: Choosing between blocking and alerting

Not every detection should page a human, and not every high-confidence detection should auto-block. The decision depends on confidence, impact, and the cost of a wrong automated action. Auto-blocking a commodity malware hash at the gateway is safe and desirable: high confidence, low collateral risk. Auto-isolating a domain controller on a lower-confidence behavioral signal is dangerous, because a false positive causes an outage that may exceed the harm the rule guards against. Between these extremes lies a spectrum of responses: enrich and score, alert to a queue, page on-call, or automate containment.

Design a response tier for each detection derived from its confidence and the blast radius of the automated action. Where automation is used, build in guardrails: rate limits so a misfiring rule cannot isolate a thousand hosts, allowlists for critical assets that require human confirmation, and an easy, audited rollback. The governing principle is that automation should reduce mean time to respond without introducing a new single point of failure. A detection assistant proposes containment but does not execute it; the boundary between recommendation and action is where human judgment and accountability live, especially for high-impact responses.

EXPLAINER: Enrichment sources and their trust levels

Enrichment pulls context from many sources, and each carries a different trust level that should be recorded alongside the value. Internal authoritative sources such as the asset inventory and identity directory are high trust but can be stale. Third-party reputation and threat-intel feeds vary widely in freshness and accuracy and can produce both false hits (a shared hosting IP flagged for one bad tenant) and false misses (a brand-new malicious domain no feed has seen). Passive DNS and WHOIS are factual but require interpretation. Behavioral prevalence computed from your own fleet is often the most reliable discriminator because it reflects your reality.

The engineering implications: never let a single enrichment source silently drive an auto-close, because its errors become your blind spots; combine sources and weight them by trust; and always timestamp enrichment so an analyst knows how fresh the context is. Cache with TTLs appropriate to volatility (asset ownership changes slowly, domain reputation quickly). When an enrichment source is unavailable, fail safe by surfacing the alert with a "context unavailable" note rather than defaulting to benign. The detection assistant should always disclose which enrichment values it relied on and their provenance, so a human can discount a conclusion built on a weak or stale source.

EXPLAINER: Why one good detection beats ten redundant ones

Detection catalogs tend to accumulate redundancy: ten rules that all key on slightly different artifacts of the same tool's defaults, all of which go dark when the attacker changes one flag. Redundancy that spans independent data sources is valuable resilience; redundancy that restates the same fragile observable is just maintenance burden and false confidence. When auditing a catalog, group rules by the underlying behavior and data source they depend on, and ask whether the group provides diverse, independent coverage or merely repeats a single brittle assumption.

The goal is defense in depth across observation vantage points: if a technique can be caught at the host by process lineage, at the network by destination behavior, and at the identity layer by anomalous authentication, three independent detections give real resilience because evading all three is expensive. Ten rules that all read the same field on the same event give the illusion of coverage. Prune ruthlessly: retire rules that add count without adding independence, and invest the freed maintenance capacity in covering a genuinely blind technique. Catalog quality is measured by independent coverage per technique, not by raw rule count.

EXPLAINER: Detecting persistence via registry and startup

Persistence ensures an intruder survives reboots and re-logons, commonly through registry Run keys, startup folders, services, scheduled tasks, and WMI subscriptions (T1547, T1543, T1053, T1546). Detection hypotheses focus on the creation or modification of these autostart locations by unexpected actors. For registry Run keys, the observable is a write to a known autostart key pointing at a binary in an unusual path (user temp, ProgramData, AppData) by a process that is not a legitimate installer. Data sources are registry-modification auditing and, where that is thin, process-lineage that shows a suspicious parent performing the write.

The false-positive profile is dominated by legitimate software installation and updates, which routinely create autostart entries. Distinguishers include the signing status and prevalence of the referenced binary, the path (system-managed versus user-writable), the installing process, and whether a change or software-deployment record exists. A durable approach baselines the set of autostart entries per host and alerts on new additions, then enriches with binary reputation. Validate by enumerating existing autostart entries fleet-wide to establish the baseline, then adding a benign test entry and a simulated malicious-looking one to confirm the rule discriminates. Persistence detection is high value because it catches intruders in a phase they cannot skip if they want durable access.

EXPLAINER: The role of deception in high-precision detection

Deception technologies, honeytokens, honeyfiles, honey accounts, decoy systems, generate detections with unusually high precision because legitimate users have no reason to touch them. A honey account that is never used for real work should never authenticate; any logon attempt against it is inherently suspicious. A honeyfile with an enticing name that no business process references should never be opened; access is a strong signal. Because the benign base rate is near zero, these detections invert the usual precision problem and produce alerts that are almost always worth investigating.

The engineering care is in placement and believability. Decoys must be discoverable by an intruder performing normal reconnaissance yet invisible to legitimate users and automated scanners that might trip them accidentally. Document every deception asset so that a well-meaning administrator or a vulnerability scanner touching it does not generate a mystifying alert, and so responders recognize a decoy hit for what it is. Deception does not replace behavioral detection; it complements it by providing a small number of very high-confidence tripwires deep inside the environment, often catching an intruder who has evaded perimeter and host detections but cannot resist the bait during lateral movement and collection.

EXPLAINER: Validating a new rule before production

Shipping a detection straight to the alert queue is how programs earn distrust. A staged validation path protects both precision and recall. First, unit-test the logic against synthetic events: at least one that must match and one near-miss that must not, encoding the rule's intended boundary. Second, run the rule in shadow mode against historical benign telemetry to estimate its false-positive volume in your real environment; this is where a rule that looked clean on paper reveals that it fires fifty times a day on a business process you forgot about. Third, confirm recall by replaying known attack telemetry or a purple-team exercise, so you know the rule actually catches what it claims.

Only after these three does the rule graduate to production, and even then it may start at a low-severity or enrichment-only tier while its live precision is observed, then be promoted once metrics confirm it. Document the validation results in the rule's metadata: the synthetic tests, the shadow-mode alert volume, and the recall evidence. This record is what a future maintainer needs to understand the rule's intended operating point and to detect drift against it. A rule with no validation history is a liability; a rule with a documented validation trail is an engineered control that others can trust, tune, and retire on evidence rather than guesswork.

EXPLAINER: Detecting credential access via authentication anomalies

Beyond memory-scraping, credential compromise surfaces at the identity layer as anomalous authentication patterns. Hypotheses include: a single account authenticating to an unusually large number of distinct systems in a short window (consistent with credential spraying outward or pass-the-hash movement, around T1550 and T1021); many accounts failing then succeeding from one source (password spraying, T1110.003); or authentication using legacy or weak protocols that modern clients should not use. Each is a statistical deviation from an established baseline of who-authenticates-to-what.

Data sources are the identity provider and domain controller authentication logs, ideally correlated with source host and protocol. The false-positive profile includes administrators and service accounts that legitimately touch many systems, vulnerability scanners, and IT automation, all of which must be characterized per cohort. A password-spraying detection thresholds on the count of distinct accounts targeted from one source with a failure-then-success pattern; the threshold comes from the benign distribution of failed authentications per source. Validate by baselining authentication fan-out per account cohort and by replaying a controlled spray in a lab tenant. Identity-layer detection is powerful because it observes the reuse of stolen credentials regardless of how they were obtained, providing an independent vantage that complements host-based credential-access rules.

EXPLAINER: The honest coverage report to leadership

Leadership deserves a coverage report that neither overstates protection nor drowns them in technical detail. The temptation is to present an all-green ATT&CK heatmap that implies comprehensive defense; the honest version communicates three things clearly. First, where coverage is deep and validated, meaning multiple independent detections tested against real or simulated attacks. Second, where coverage is thin or theoretical, meaning a single brittle rule or a rule untested against actual behavior. Third, where there is no coverage at all, especially for techniques relevant to the organization's threat model, and why, whether it is a missing log source, a backlog item, or an accepted risk.

Pair the coverage picture with the metrics that show the program is alive: alert precision trends, mean time to triage, the number of detections that trace to real incidents, and the results of the most recent purple-team exercise. Frame gaps as a prioritized plan with prerequisites and costs, not as failures. This honesty builds durable trust and funds the program, because leaders can make informed risk decisions. A green wall invites complacency and collapses the first time a covered technique leads to a breach; a candid, measured report positions security as an engineering discipline that manages risk transparently rather than a function that promises certainty it cannot deliver.

EXPLAINER: Composing detections into an attack narrative

Individual alerts are fragments; the value to a responder is the assembled narrative of an intrusion. Detection engineering should therefore consider not only whether a single behavior fires but how alerts chain into a story across the kill chain: initial access, execution, persistence, privilege escalation, credential access, discovery, lateral movement, collection, and impact. A correlation layer that links alerts sharing an entity (host, account, session) into an incident timeline turns a scattered queue into a coherent case, dramatically reducing time to understanding.

This composition also improves precision at the case level. A lone execution alert may be ambiguous, but the same alert followed by persistence, then credential access, then lateral movement, forms a pattern whose joint likelihood of being benign is tiny. Engineering this requires stable entity resolution so events are correctly attributed, and a scoring model that raises case severity as more kill-chain phases light up for the same entity. The design goal is that a responder opening a case sees the sequence of observed behaviors, each tagged with its confidence and data source, rather than ten disconnected alerts. Narrative composition is where detection engineering meets incident response, and it is often where the largest gains in analyst effectiveness are found.

EXPLAINER: Knowing the limits of your detection

Intellectual honesty about blind spots is itself a security control, because unknown gaps are exploited gaps. Every detection program should maintain an explicit inventory of what it cannot see: unmanaged devices without endpoint telemetry, encrypted traffic it does not inspect, cloud or SaaS actions for which it collects no logs, techniques with no current rule, and time periods or hosts where a log source was down. This inventory is uncomfortable to compile precisely because it enumerates weakness, which is exactly why it is valuable; an adversary will find these gaps whether or not you have written them down.

The inventory drives action. Some gaps become backlog items to close by adding telemetry or rules; others are accepted risks that leadership signs off on with eyes open; still others are mitigated by compensating controls at a different layer. It also calibrates confidence during incidents: when an assistant or analyst reports "no malicious activity detected," that claim must be qualified by coverage, because absence of alerts is not absence of activity where visibility is thin. The mature posture states plainly what was and was not observable, marks the unobserved as unknown rather than benign, and treats every newly discovered blind spot as a finding worth remediating. A program that knows and documents its limits is far stronger than one that mistakes a quiet queue for a secure environment.
